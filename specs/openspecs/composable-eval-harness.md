# Composable Evaluation Harness Specification

## Overview

zkast is a **composable evaluation harness** for knowledge-creation and retrieval frameworks — it sits upstream of product decisions. Its purpose is to open the black box: define many **compositions** of an ingestion-and-retrieval pipeline, run them over the same data, collect comparable metrics, and form grounded opinions about which framework, ontology, and retrieval choices confer which advantages.

The pipeline is decomposed into a small set of **swappable, versioned stages**. A named composition of stage choices is a **Pipeline Configuration**. Configurations are the unit of ingestion, retrieval, and comparison: any single stage can be varied while the others are held constant, so an observed metric delta can be attributed to a specific stage choice.

This specification generalizes the existing single, hardcoded pipeline (parse → atomic notes → Graphiti/LangExtract graph extraction → graph retrieval) into the harness, and adds Microsoft GraphRAG as the first new extractor+retrieval plugin. It supersedes the implicit "one fixed backend" assumption in the core specs.

## Requirements

### Functional Requirements

- **FR-1**: The pipeline is composed of ordered stages — **Parse/Chunk**, **Extraction**, **Graph Store/Index**, **Retrieval** — each fulfilled by a selectable, registered **stage plugin**. The chain is **fixed and linear**; users vary stage implementations and parameters, not topology.
- **FR-2**: The **Extraction** stage is the product of an **extractor engine** (e.g. Graphiti typed extraction, LangExtract grounded extraction, GraphRAG native extraction) and an **ontology/prompt set** (the entity/edge type definitions plus extraction instructions).
- **FR-3**: An **ontology/prompt set** is a first-class, **versioned** artifact. It can be authored **manually** (edit entity/edge types and instructions) and generated by **auto-tuning** (sample the corpus and propose a domain-adapted ontology/prompts). Auto-tuning produces a new editable version.
- **FR-4**: A **Pipeline Configuration** is a named composition `{ extractor, ontology/prompt-set version, graph store, retrieval strategy, model provider }`. It is **versioned and content-hashed** so any run can be pinned to the exact composition that produced it.
- **FR-5**: Configurations have a canonical **portable representation** (a declarative document) that can be exported, version-controlled, and seeded; the runtime system also keeps configurations in a queryable registry.
- **FR-6**: Operators can **run ingestion** with a configuration (producing that configuration's graph artifacts for a memory space) and **retrieve/chat** with a configuration.
- **FR-7**: Operators can run a **comparison**: a matrix of configurations over the same dataset/questions, including the special case of holding all stages constant and varying exactly one stage, to isolate that stage's effect.
- **FR-8**: Comparison results record the **full composition** (not just the retrieval strategy) and surface **per-stage attribution** so a metric delta can be ascribed to a stage choice (e.g. ontology generic vs auto-tuned).
- **FR-9**: The **model provider** for a plugin is configurable: a Cohere OpenAI-compatible endpoint by default, with optional bring-your-own OpenAI/Azure credentials, so the harness can also compare provider effects.
- **FR-10**: Microsoft GraphRAG is available as an extractor+index plugin (batch community indexing) and as a retrieval plugin (community local/global search), runnable **in parallel** with the Graphiti backend over the same content for side-by-side comparison.
- **FR-11**: Existing behavior is preserved: the current parse → notes → Graphiti+LangExtract → graph-retrieval pipeline is expressible as a built-in default configuration with no change in output.

### Non-Functional Requirements

- **NFR-1**: **Reproducibility** — a recorded result must identify the exact configuration (content hash + version), dataset version, and provider so it can be re-run.
- **NFR-2**: **Isolation** — each configuration's graph artifacts are scoped per memory space and per configuration; running a new configuration must not corrupt another's artifacts or the production graph.
- **NFR-3**: **Cost/throughput safety** — expensive batch indexing (e.g. GraphRAG full index) must run on a controlled, capped queue and must not starve interactive chat or other ingestion.
- **NFR-4**: **Extensibility** — adding a new extractor, store, or retrieval plugin must not require changing unrelated stages; plugins register against stage contracts.
- **NFR-5**: **No silent drift** — adding a stage plugin or changing a configuration schema updates the relevant spec per the spec-maintenance convention.

## Data Model

### Pipeline Configuration

**Purpose**: A named, versioned composition of stage choices; the unit of ingestion, retrieval, and comparison.

**Fields:**
- `id`, `workspace_id`: identity / ownership.
- `name`, `description`: human label.
- `extractor`: selected extractor plugin id.
- `ontology_version`: reference to a Prompt Set version (nullable for extractors with no external ontology).
- `graph_store`: selected store plugin id.
- `retrieval_strategy`: selected retrieval plugin id.
- `provider`: model-provider selector + model identifiers for this configuration.
- `params`: per-stage parameters (e.g. community levels, chunk size, top-k).
- `version`, `content_hash`: bump/hash on any field change; results pin these.
- `is_builtin`: marks the seeded default(s).
- `created_at`, `updated_at`.

**Constraints:** unique `(workspace_id, name, version)`; `content_hash` derived from the normalized composition.

### Prompt Set (ontology + extraction prompts)

**Purpose**: Versioned entity/edge ontology and extraction instructions consumed by the extraction stage.

**Fields:**
- `id`, `workspace_id`, `name`, `version`.
- `entity_types`, `edge_types`: typed ontology (names, descriptions, allowed edge pairings).
- `instructions`: extraction guidance.
- `origin`: `generic` | `manual` | `auto`.
- `derived_from_version`: lineage for auto-tuned/edited versions.
- `created_at`.

**Constraints:** unique `(workspace_id, name, version)`; an immutable version is referenced by configurations and runs.

### GraphRAG Index (artifact pointer)

**Purpose**: Tracks a built GraphRAG artifact set for one memory space + configuration.

**Fields:**
- `id`, `workspace_id`, `agent_id` (memory space), `configuration_id`.
- `status`, `artifact_uri`, `stats` (community/entity/relationship counts), `prompt_set_version`.
- `started_at`, `ended_at`, `failure_reason`.

### Eval run (extended)

**Additional:** an eval run records the **composition** per result (extractor, ontology version, store, retrieval, provider, configuration content hash) so comparisons attribute deltas to stages, not just to a coarse retrieval-mode label.

## Business Rules

### Rule: Fixed linear topology
**Description**: A configuration is a fixed ordered chain (Parse → Extract → Store → Retrieve). Composition varies implementation/params per stage, never wiring/branching.

### Rule: Pin results to composition
**Description**: Every comparison/eval result stores the configuration's `content_hash` + `version`, dataset version, and provider. A result whose configuration changed is not silently re-attributed.

### Rule: Artifact isolation per configuration
**Description**: Ingesting with a configuration writes only that configuration's store/artifacts for the memory space; it must not overwrite another configuration's artifacts or the default production graph unless the configuration explicitly targets it.

### Rule: Ontology version immutability
**Description**: A Prompt Set version, once referenced by a run, is immutable; edits create a new version (lineage via `derived_from_version`).

### Rule: Provider scoping
**Description**: A configuration's provider selection governs that configuration's LLM/embedding calls only; it does not change the workspace default provider.

## User Flows

### Flow: Author a configuration
**Trigger**: Operator opens the Pipelines/Lab and creates/clones a configuration.
**Steps:** choose extractor, ontology/prompt-set version, store, retrieval, provider, and per-stage params via a structured editor; save (new version + content hash); optionally export the portable document.
**Success Outcome**: a registered, versioned configuration available for ingestion/retrieval/comparison.

### Flow: Tune an ontology
**Trigger**: Operator edits an ontology (manual) or runs auto-tune over a memory space's corpus.
**Steps:** manual edit produces a new Prompt Set version; auto-tune samples the corpus, proposes a domain-adapted ontology + instructions, and writes a new editable version (lineage recorded).
**Success Outcome**: a new ontology version attachable to a configuration; "generic vs tuned" becomes a comparable axis.

### Flow: Run a comparison
**Trigger**: Operator selects two or more configurations and a dataset/questions.
**Steps:** the harness ingests/queries each configuration over the same inputs, scores results, and presents them side by side with each configuration's stage-strip and per-stage attribution.
**Success Outcome**: comparable metrics with the varied stage clearly identified.

### Flow: Parallel Graphiti vs GraphRAG
**Trigger**: Operator enables both a Graphiti-based and a GraphRAG-based configuration for a memory space.
**Steps:** both index the same content into their own stores; chat/eval can query either; comparison runs them head to head.
**Error Outcomes**: provider/credential errors, GraphRAG index not built, or rate limiting surface as actionable status; partial results are not silently scored as complete.

## Authorization

### Permission: Manage configurations and tuning
**Required Role**: workspace member with settings/manage capability (same level as configuring pipeline credentials).
**Resource-Level**: only the same workspace's configurations, prompt sets, artifacts, and credentials.

## Validation Rules

- **Configuration**: extractor, store, and retrieval must reference registered plugins; ontology version (if set) must exist; provider credentials must be present for the selected provider before a run.
- **Prompt set**: at least one content-bearing entity type; edge pairings reference defined entity types.
- **Comparison**: all selected configurations must be runnable (built/available) before a comparison starts, or the run reports which are not.

## User Interface Requirements

### View: Pipelines / Lab (primary surface)
**Purpose**: Browse, author, select, run, and compare configurations.
**Display Elements:** configurations shown as horizontal **stage-card strips** (Parse → Extract[engine + ontology vN] → Store → Retrieve), with per-stage params on expand; an in-app **structured form editor** (per-stage selectors + params) that round-trips to the portable representation.
**Actions Available:** create/clone/edit a configuration; multi-select to compare; launch interactive chat-compare and batch eval; export a configuration.
**States:** none/empty, draft, saved, running, results.

### View: Comparison results
**Purpose**: Side-by-side outcomes for a configuration matrix.
**Display Elements:** stage-strip headers per column/row; per-question and aggregate scores; per-stage attribution (which stage choice moved the metric).

### View: Status / coverage
**Purpose**: Per memory space and per configuration health.
**Display Elements:** graph store / GraphRAG index built? + counts; active ontology version; staleness vs ingested content.

## Edge Cases

- **Unbuilt GraphRAG index**: a GraphRAG retrieval configuration queried before its index is built returns a clear "index not built" state, not an empty answer.
- **Stale index**: when new content is ingested after an index was built, status flags the configuration as stale and offers a rebuild.
- **Provider mismatch**: selecting a provider without credentials blocks runs with an actionable message.
- **Ontology drift between arms**: when comparing engines that each did their own extraction, the comparison clearly labels that extraction differed (so deltas are not misread as pure retrieval differences); the "shared ontology feeding both arms" mode is a distinct, later option.

## Acceptance Criteria

- [ ] AC-1: The current production pipeline is expressible as a built-in default configuration with byte-for-byte equivalent graph output (no behavior change).
- [ ] AC-2: A new extractor, store, or retrieval plugin can be added by registering against the stage contract without modifying other stages.
- [ ] AC-3: An ontology/prompt set can be edited manually and auto-tuned; both produce new immutable versions with lineage.
- [ ] AC-4: A configuration can be authored in the Lab, exported to and re-imported from its portable representation, and is content-hashed.
- [ ] AC-5: MS GraphRAG can index a memory space (configurable provider) and answer via community search, in parallel with a Graphiti configuration over the same content.
- [ ] AC-6: A comparison run over a configuration matrix records each result's full composition and shows per-stage attribution.
- [ ] AC-7: Expensive batch indexing runs on a capped/isolated queue and does not starve interactive chat.
- [ ] AC-8: Results are reproducible from the recorded configuration content hash + dataset version + provider.

## Success Metrics

- An operator can define two configurations that differ by exactly one stage (e.g. ontology generic vs auto-tuned, or Graphiti vs MS-GraphRAG retrieval), run them over a shared dataset, and read a per-stage attribution of the metric delta — without manual SQL.
